# Auth & Database Plan (Supabase)

## Context

WeaveDiary today is frontend-only — landing page plus a mock dashboard at `/dashboard/*`. The "Sign in" button on the landing nav (`app/app/page.tsx:38`) links straight to `/dashboard` with no guard, and the dashboard renders mock data from `app/lib/mock/`. There is no `package.json` entry for any auth or database library, no `.env*` file, and no `process.env.*` usage in the codebase.

To unblock everything downstream (real entries, integrations, voice notes, reviews) we need user identity and a database. Confirmed decisions:

- **Supabase** for Postgres + Auth (managed) — no Prisma. Schema and types managed via Supabase CLI.
- **Email/password + Google OAuth** sign-in.
- **Email confirmation enforced** for password sign-ups (Supabase default).
- **Initial schema scope**: `profiles` and `integrations` only. Entries/goals/reviews/voice_notes land in later migrations alongside their features.
- **`/dashboard/*` is auth-guarded** via Next.js middleware — unauthenticated users are redirected to `/sign-in`.

---

## Outcome

- `npm run dev` starts a fully wired Supabase-backed app:
  - `/sign-up` and `/sign-in` pages on the parchment design system, with email/password and a "continue with Google" button
  - OAuth callback at `/auth/callback` (PKCE flow)
  - Sign-out POST route at `/auth/sign-out`
  - `middleware.ts` refreshes the session on every request and redirects unauthenticated traffic away from `/dashboard/*`
  - Dashboard topbar shows the real signed-in user (name + email from Supabase, replacing any mock user data)
- A `supabase/` workspace with the initial migration creating `profiles` and `integrations` plus their RLS policies and a `handle_new_user` trigger that auto-creates a profile row on signup
- Generated `lib/database.types.ts` so server code is fully typed against the schema
- `.env.local.example` documents the three required Supabase env vars

Out of scope: actual Gmail/GitHub/Slack OAuth integration flows (those live behind the `integrations` row, but the connector code is later work). Voice transcription, entry generation, and the Claude API are also unchanged.

## Schema (migration `0001_init_profiles_integrations.sql`)

Two tables. Both reference `auth.users(id)` (managed by Supabase). Both have RLS on, with policies scoped to `auth.uid()`.

```sql
-- profiles: public-ish user metadata, mirrors auth.users 1:1
create table public.profiles (
  id           uuid primary key references auth.users(id) on delete cascade,
  email        text not null,
  full_name    text,
  avatar_url   text,
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now()
);

alter table public.profiles enable row level security;

create policy "profiles are viewable by owner"
  on public.profiles for select using (auth.uid() = id);
create policy "profiles are updatable by owner"
  on public.profiles for update using (auth.uid() = id);

-- auto-create profile when a new auth.users row is inserted
create function public.handle_new_user()
returns trigger language plpgsql security definer set search_path = public as $$
begin
  insert into public.profiles (id, email, full_name, avatar_url)
  values (
    new.id,
    new.email,
    new.raw_user_meta_data ->> 'full_name',
    new.raw_user_meta_data ->> 'avatar_url'
  );
  return new;
end; $$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();

-- integrations: one row per (user, platform) connected source
create type public.integration_provider as enum
  ('gmail', 'github', 'slack', 'discord', 'google_calendar');

create type public.integration_status as enum
  ('connected', 'disconnected', 'error');

create table public.integrations (
  id              uuid primary key default gen_random_uuid(),
  user_id         uuid not null references auth.users(id) on delete cascade,
  provider        public.integration_provider not null,
  status          public.integration_status not null default 'connected',
  external_account_id text,           -- e.g. github login, gmail address
  scopes          text[] not null default '{}',
  connected_at    timestamptz not null default now(),
  last_synced_at  timestamptz,
  unique (user_id, provider)
);

alter table public.integrations enable row level security;

create policy "integrations are viewable by owner"
  on public.integrations for select using (auth.uid() = user_id);
create policy "integrations are insertable by owner"
  on public.integrations for insert with check (auth.uid() = user_id);
create policy "integrations are updatable by owner"
  on public.integrations for update using (auth.uid() = user_id);
create policy "integrations are deletable by owner"
  on public.integrations for delete using (auth.uid() = user_id);
```

Note: OAuth refresh/access tokens for connected integrations are **not** stored in the `integrations` table — per the privacy requirements in `CLAUDE.md`, raw credentials should never be stored. Token refresh will go through Supabase's `provider_token` mechanism or a vault table in a later migration.

## Implementation Steps

### 1. Install packages and scaffold env

In `app/`:

```bash
npm install @supabase/supabase-js @supabase/ssr
```

Create `app/.env.local.example`:

```
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
# Server-only — never expose to the browser. Used for migrations / admin scripts.
SUPABASE_SERVICE_ROLE_KEY=
```

User creates a real `app/.env.local` from this template after creating the Supabase project. Verify `.env.local` is gitignored (Next.js's default covers it).

### 2. Initialize Supabase project (manual + CLI)

User-driven (cannot be automated):
1. Create a new project at supabase.com, copy URL + anon key + service-role key into `.env.local`.
2. In **Authentication → Providers**: enable Email (with "Confirm email" on, the default), and enable Google — paste a Google Cloud OAuth client ID/secret. Set the redirect URL to `http://localhost:3000/auth/callback` for dev.
3. In **Authentication → URL Configuration**: set Site URL to `http://localhost:3000` and add the same callback to "Redirect URLs".

CLI-driven:

```bash
npx supabase init        # creates supabase/ workspace
npx supabase link --project-ref <ref>
npx supabase db push     # applies 0001_init_profiles_integrations.sql to remote
npx supabase gen types typescript --linked > app/lib/database.types.ts
```

### 3. Build the Supabase client helpers

Three files, all under `app/lib/supabase/`. These follow the official `@supabase/ssr` pattern for Next.js App Router.

- `client.ts` — `createBrowserClient<Database>(url, anon)` — used in client components only.
- `server.ts` — `createServerClient<Database>(url, anon, { cookies })` — used in RSCs, server actions, route handlers. Wires Next's `cookies()` API.
- `middleware.ts` — `updateSession(request)` — refreshes the auth cookie on every request, returns the mutated `NextResponse`. Required because Server Components can't write cookies; the middleware does it for them.

### 4. Add root middleware

`app/middleware.ts`:

```ts
import { updateSession } from '@/lib/supabase/middleware';
import { NextRequest, NextResponse } from 'next/server';

export async function middleware(request: NextRequest) {
  const { response, user } = await updateSession(request);

  const { pathname } = request.nextUrl;
  const isProtected = pathname.startsWith('/dashboard');
  const isAuthRoute = pathname === '/sign-in' || pathname === '/sign-up';

  if (isProtected && !user) {
    const url = request.nextUrl.clone();
    url.pathname = '/sign-in';
    url.searchParams.set('next', pathname);
    return NextResponse.redirect(url);
  }
  if (isAuthRoute && user) {
    const url = request.nextUrl.clone();
    url.pathname = '/dashboard';
    return NextResponse.redirect(url);
  }
  return response;
}

export const config = {
  matcher: ['/((?!_next/static|_next/image|favicon.ico|brand/|.*\\.svg$).*)'],
};
```

### 5. Build sign-in and sign-up pages

Both pages live under `app/(auth)/` (route group — keeps them out of the dashboard layout, doesn't add a URL segment).

Visual treatment, matching the existing design system:
- Centered `.wd-card` (10px radius, `var(--shadow-1)`) on a `--color-parchment` background
- Serif `var(--type-h1)` heading ("Welcome back" / "Begin weaving")
- Inter Tight body, JetBrains Mono for the small "or" divider label
- Inputs styled inline with design tokens (no `.wd-input` exists yet — match the inline input pattern at `app/app/page.tsx:335`)
- Primary `.btn-primary` for submit, `.btn-secondary` for the Google button (with `/brand/google.svg` icon — add asset)
- Madder `var(--color-madder)` link to switch between sign-in and sign-up

`EmailPasswordForm.tsx` — client component using a **server action** for submit. Server action calls `supabase.auth.signInWithPassword({ email, password })` (sign-in) or `signUp({ email, password, options: { emailRedirectTo: '/auth/callback' } })` (sign-up). On success, redirect to `searchParams.next ?? '/dashboard'`. On error, `useFormState` displays the message above the submit button.

`GoogleButton.tsx` — client. On click:

```ts
const supabase = createBrowserClient(...);
await supabase.auth.signInWithOAuth({
  provider: 'google',
  options: { redirectTo: `${location.origin}/auth/callback?next=${next}` },
});
```

Sign-up "check your email" state — after a successful `signUp` call (when confirmation is required, Supabase returns a user but no session), swap the form for a serif paragraph: *"Sent a confirmation link to {email}. Click it to finish signing up."*

### 6. Add auth route handlers

`app/auth/callback/route.ts` — `GET`:
1. Read `code` and `next` from `request.nextUrl.searchParams`.
2. `await supabase.auth.exchangeCodeForSession(code)`.
3. Redirect to `next ?? '/dashboard'` on success, or `/sign-in?error=...` on failure.

`app/auth/sign-out/route.ts` — `POST`:
1. `await supabase.auth.signOut()`.
2. Redirect to `/`.

### 7. Wire the real user into the dashboard topbar

`app/app/dashboard/_components/shell/Topbar.tsx` is currently a server component. Read the session there:

```ts
const supabase = await createServerClient();
const { data: { user } } = await supabase.auth.getUser();
```

Pass `user.email` and the `full_name` / `avatar_url` from the `profiles` row into the existing topbar slot that today shows mock user data. Add a small sign-out form that POSTs to `/auth/sign-out`.

### 8. Update the landing nav

`app/app/page.tsx:38` — change the "Sign in" `Link` from `href="/dashboard"` to `href="/sign-in"`. Change "Begin weaving" CTA from `href="#cta"` to `href="/sign-up"` (the email capture form at `#cta` is now redundant — leave the section visual but point its submit button at `/sign-up?email={value}` so prefill is preserved).
